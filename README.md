backend、agent 和 rag 是同一个仓库中的 Python 包。HTTP 模式中，聊天 Agent 和订单 API 由同一个服务进程提供，工具仍通过 HTTP 调用订单接口；可选的终端入口运行在另一个进程。所有命令从仓库根目录执行，使用 `python -m`，无需 sys.path 修改或旁边的旧 Demo。原 order-agent 与 rag-demo 保留作学习阶段记录。

终端 `main()` 登录成功后调用 `initialize_agent()`；HTTP 服务则在 lifespan 中调用，并复用返回对象。制度工具通过闭包保留公共资源，业务工具通过 runtime.context 读取本次凭证；两者不混用。order_client 的 headers 携带身份，params 携带查询条件，json 携带登录或工单正文，后端从凭证确认 user_id。create_support_ticket 从 runtime.config 读取本次 thread_id。导入模块不会执行终端 main，也不会直接加载模型。

## 环境与启动（PowerShell）

使用 Python 3.12。新克隆环境按以下步骤准备：

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
```

第一次复制后，手动在 `.env` 中填写自己的 `DEEPSEEK_API_KEY` 和 `POSTGRES_PASSWORD`。已有 `.env` 时不要再次复制覆盖。首次运行会下载两个模型到 `.model_cache`；模型推理在本机 CPU 执行，DeepSeek 回答通过 API 调用并产生相应费用。原项目的密钥、数据库、模型缓存和虚拟环境没有搬进新目录。

业务数据库现改为 PostgreSQL，通过 psycopg 3 连接。先启动 PostgreSQL，在 pgAdmin 中创建可登录的项目账号 `support_app` 和由它拥有的数据库 `customer_support`；账号无需超级用户、创建角色或创建数据库权限。按实际安装填写 `.env` 的 POSTGRES_HOST、POSTGRES_PORT、POSTGRES_DB、POSTGRES_USER 和 POSTGRES_PASSWORD，默认连接本机5432端口。数据库密码与演示顾客密码无关。settings 使用 SQLAlchemy URL.create 组装连接，不手动拼接密码；另转换为原生PostgreSQL连接字符串供保存器使用，其中包含真实密码，不打印或提交该值。业务表与检查点表使用同一个数据库，分别由SQLModel和PostgresSaver管理；检查点表在服务启动的setup中准备。

先初始化演示数据库：

```powershell
.\.venv\Scripts\python.exe -m backend.seed_demo
```

脚本在配置的 PostgreSQL 数据库中创建缺少的业务表并写入演示数据：U1001（alice）拥有 A1001、A1002，U1002（bob）拥有 A2001，三笔订单均已发货。密码通过 pwdlib/Argon2 生成哈希后保存；演示密码分别为 `demo-password` 和 `demo_password_2`。重复运行会跳过已存在的编号，不覆盖已有记录。初始化脚本通过模块方式运行，不直接执行 backend/seed_demo.py。create_all 只创建缺少的表，不创建数据库、不迁移已有表结构，也不会把旧 SQLite 的记录自动搬过来；旧文件可保留，旧凭证和会话编号不会因此在新库生效。

1. 调用 `POST /login`，请求正文为 `{"username":"alice","password":"demo-password"}`。
2. 从响应复制 `access_token`，点击 Authorize，只粘贴原始凭证。客户端请求头为 `Authorization: Bearer <token>`。
3. 调用 `/me` 得到当前用户；Alice 的列表只有 A1001/A1002，访问 Bob 的 A2001 返回 404。替换为 Bob 的凭证后列表只有 A2001。
4. 调用 `/logout` 返回 204，保留旧凭证再次查询应返回 401；重新登录取得新凭证后恢复。

### HTTP 聊天验收

保持 Alice 的有效授权，调用 `POST /chat`：

```json
{"question":"帮我查询 A1001 的订单状态"}
```

预期200，返回 `conversation_id` 和 `answer`。保存会话编号，用它继续提问：

```json
{"question":"我刚才查询的是哪个订单？","conversation_id":"替换为实际会话编号"}
```

预期仍为同一编号，模型能根据历史指出 A1001。随后登录 Bob 并替换 Authorize 中的凭证，`GET /me` 确认身份，再携带 Alice 的编号请求 `/chat`，预期404，在执行 Agent 前拒绝。首次请求省略编号或传null表示新会话，未知编号不会自动创建。空白问题422，无效凭证401。

顾客网页使用相同的`/chat`接口；接口文档验收不等于完整浏览器验收。进程重启后归属记录仍在，内存消息会丢失；网页刷新后也不会恢复旧聊天。

凭证保存在数据库中的形式是 SHA-256 哈希，用户密码使用 pwdlib/Argon2；身份验证不会把密码哈希返回客户端。有效期由 `LOGIN_SESSION_TTL_SECONDS` 控制，当前为一小时。过期记录即使尚未删除，也不能通过验证；修改有效期只影响之后签发的会话。到期测试已用一分钟配置完成，随后恢复一小时。

数据库独立于旧 Demo；已有数据库不会因为 Python 模型修改而自动迁移。当前使用带 user_id 的新项目数据库，示例数据由 seed_demo 准备。

如需使用原终端聊天入口，保持后端运行，在另一个终端启动。这个入口会另外创建自己的 Agent 和内存历史，不与 HTTP 聊天历史共用：

```powershell
.\.venv\Scripts\python.exe -m agent.langchain_agent_demo
```

终端输入 alice / demo-password 登录。可依次验证：

1. `查询 A1001 的订单状态`：返回本人订单；`查询 A2001 的订单状态`：未找到可访问订单，不展示 Bob 数据。
2. `帮我查一下手机的订单`：query_orders 使用 product_keyword 找到 A1002，随后可查询详情。
3. 输入 `新会话`，问 `我已经发货的订单还能退款吗？`：列出两笔候选并请用户选择；回复 `手机那一笔` 后结合详情与制度回答，缺条件继续询问。
4. 每轮业务问题进入 invoke 前，程序调用 /me 检查身份；401 提示并退出，连接或其他 HTTP 错误提示后等待下一次输入。验证自然到期时临时把有效期设60秒，重启服务和 Agent，测试后恢复一小时。

输入 `新会话` 或 `新对话` 更换 thread_id，输入 `q` 退出。InMemorySaver 仅保留当前进程内的历史，退出后不会恢复；消息数包含工具调用和工具返回，不等于问题数或 token 数。thread_id 不代替登录身份，后续还需把会话归属绑定到可信用户。终端版每次启动登录并创建自己的 Agent；网页版应由聊天后端验证请求身份及会话拥有者。

当前详情未找到订单返回通用错误，列表无匹配返回 []，凭证失效返回错误字典，服务故障不当作空结果。invoke前检查不保证整轮有效，订单API仍逐请求验证。执行中的HTTPX HTTPError和模型SDK APIError在聊天循环捕获：提示后启新会话，跳过本轮后续打印，不自动重跑失败问题。失败可能留下未配对工具消息，旧状态保留；工单也可能已保存，需核对结果。手动重提仍可能重复，幂等未实现。步骤上限、未知异常及完整分页策略仍待补。
